# Pre-launch security and performance review, 1 October 2026

Launch checklist step 6. A code-level review of the client (`even-app`) and the sync server (`even-server`). It
takes two viewpoints:

- a hostile reader of the open-source code;
- a user with a very large group.

It was a reading-and-tests review. No simulator, emulator, Metro or device was used, and nothing was pushed.
`CLAUDE.md`, `design.md`, `../even-server/THREAT-MODEL.md` and `../even-server/PROTOCOL.md` define what the system
promises. This document checks the code against them.

## What was done

- **Read:** the whole crypto, validation, reducer, sync, storage, secrets, invite and rotation path in the client,
  and the Worker in full.
- **Delegated, then spot-checked:** three parallel read-throughs covered the landing page and contact Worker, the
  Python reference server, and the React list layer. Their key claims were re-checked before going in here. Where a
  finding comes from a read-through that was not re-run here, it says so.
- **Measured:** a synthetic 10,000-event group was built through `packages/core` and the real store (`node:sqlite`),
  then timed at every stage of open, join and move.
  - **Hermes proxy:** each stage ran twice, once in V8 with its JIT and once with `--jitless`. Hermes in a release
    build runs bytecode without a JIT, and V8 without one is the closest thing measurable on a Mac. Device numbers
    will differ (see the end of this document).
- **Verified with harness tests:** two attacks, run against the app's own services (`src/state/testHarness.ts`) and
  a protocol-faithful fake server. These tests were throwaway and are not committed.
- **Audited dependencies:** `npm audit` (read-only) in `even-app`, `even-server/worker` and `even-server/conformance`.
- **Checks after the fixes:**
  - even-app: `npm run typecheck`, `npm run lint`, `npx vitest run` (970 passed, 10 skipped) and
    `npm test -w @even/core` (994 passed).
  - even-server: the Worker's `npm test` (68 passed). No even-server file was changed.

## Findings by severity

Line numbers are as of `c2455d0` (before this review's commits) unless a line says otherwise.

### Critical

None. The crypto boundary holds: per-server tokens, AAD binding, random ids and nonces, 256-byte padding, no key
material on the wire, strict envelope and body validation, and nothing decrypted written by the app beyond what is
listed in M3.

### High

**H1. One valid event could crash every member's app at launch. Fixed in `7312c1f` and `6c7b6e3`.**

- **Where:**
  - The validator checks only a currency code's shape (`packages/core/src/schema.ts:20`, `CURRENCY_RE`).
  - `formatMinor` throws `RangeError` for a code the frozen ISO 4217 table lacks (`packages/core/src/money.ts:70-73`).
  - The screens called it during render, at `src/components/MoneyText.tsx:45`, `src/features/groups/GroupCard.tsx:42`,
    `src/features/group/GroupTabs.tsx:65` and `:140`, `src/components/CategoryBar.tsx:27` and
    `src/features/expense/ExpenseDetailView.tsx:73`.
  - No route exports an `ErrorBoundary`.
- **Scenario:** a member writes `group.created { currency: "ZZZ" }` with `ts` at the range floor (2024-01-01), so it
  sorts first and wins. Alternatively, any `expense.added` in `ZZZ` crashes Expenses through its row. Every member's
  Groups list, which renders `GroupCard` with the group's currency, then throws on every launch. Leave is reached
  through the group, so there is no way out. A newer client whose ISO table adds a currency would do the same to
  older builds.
- **Fix (done):**
  - Core `displayMinor` is `formatMinor` with the plain-integer fallback that the reducer's summaries and the CSV
    export already use. The display call sites now use it.
  - An unknown group currency sets `updateRequired`, so the existing "Update Even" banner shows. Group offers no Add
    expense or Settle.
  - Expense detail offers no Edit, Delete or Restore for an expense in an unknown currency, and the edit sheet builds
    no draft for one.
  - `design.md` "Schema evolution" records the rule.
- **Recommended next:** a root `ErrorBoundary` drawn as the StartupError board, so the next render throw nobody
  foresaw is not fatal. It needs a board on the canvas.

**H2. One far-future group event makes a group read-only for everyone, permanently, and rotation carries it over.
Open.**

- **Where:**
  - The validator admits any `ts` below 2100-01-01 (`packages/core/src/constants.ts:11-12`).
  - `nextTs` (`packages/core/src/hlc.ts:14-27`) gives an untargeted event `max(now, lastSeen + 1)` and ignores events
    more than 24 h ahead.
  - `group.unarchived` is untargeted (`src/state/groups.ts:909-915`, `:1636`).
  - The reducer applies archive/unarchive in `(ts, id)` order (`packages/core/src/reduce.ts:336`).
  - Rotation copies every non-control event, and `group.archived` is not one (`src/state/log.ts:13-17`,
    `src/state/groups.ts:1074`).
- **Scenario (verified with a harness test):**
  - A member writes `group.archived` with a `ts` decades ahead. A hostile one picks `4_102_444_799_999`; a phone
    whose clock reads 2099 does the same by accident. The group turns read-only on every phone.
  - Unarchive writes an event at `now`, which loses, and nothing tells the user.
  - Regenerate invite, the documented remedy for a hostile member, copies the archive into the new group, which is
    read-only too.
  - The same mechanism pins `group.renamed` and `member.updated`. Any expense with an `expense.updated` at
    `tsMax − 1` can never be edited or deleted again: its next event would need `ts = tsMax`, and the write gate says
    "check your phone's date".
  - Choosing a member to remove during rotation fails the same way if that member has a far-future event about
    themselves. The `member.archived` mark cannot be written, so the whole rotation throws.
- **Fix (recommended; this is a design decision):**
  - Rotation leaves group-level toggles (`group.archived`, `group.unarchived`, `group.renamed`) behind with the
    control events. The rotator re-states the current name and archive state in the new group.
  - Last-writer-wins gains a rule that depends only on the log: an event more than the 24 h absorb window ahead of
    every event by another device does not win a group-level or member-level field until the log catches up.
  - Rotation's removal writes `member.archived` even when its `ts` cannot beat a far-future one, and says so, instead
    of failing the rotation.

**H3. Opening, joining and moving a large group blocks the JS thread for seconds, and the lists mount every row.
Partly fixed.**

- **Measured:** see the timings table below.
  - Opening a 10,000-event group cold takes 2.5 s with `--jitless`. Joining one takes 7.9 s; moving it, 7.7 s.
  - On the public server the 2 MB cap limits a group to about 3,400 events of this mix: 548 bytes of ciphertext per
    event on average, plus 64 bytes stored per event. That is a third of these numbers. A self-hosted server with
    larger caps reaches 10,000.
- **Where:**
  - **Decrypt-all-on-open is the dominant cost.** `open` takes about 0.2 ms per envelope with `--jitless`; the loop is
    at `src/state/groupState.ts:483-504`.
  - **The Groups list derives every group before it shows anything** (`groupState.ts:651-657`), so launch costs the
    sum of every group's decrypt.
  - **Join decrypts everything three times:**
    1. The pull classifies each envelope (`src/services/sync/engine.ts:256-300`).
    2. `refreshNameCache` opens every readable envelope again to find the naming events (`engine.ts:679-699`,
       called at `:757`).
    3. The derive opens them a third time. Its decode cache is separate from the engine's.
  - **`moveServer` and rotation** reseal the whole log inside one SQLite transaction on the JS thread
    (`engine.ts:1060-1069`, `src/state/groups.ts:1064-1092`).
  - **Expenses and Activity render every row** in the one ScrollView (`GroupTabs.tsx:55`, `:167`, `:175`, inside
    `GroupScreen.tsx:386`): 6,000 and 10,000 rows mounted. No row is memoised.
  - **The usage meter** re-parses every envelope (`src/services/sync/usage.ts:41-51`).
- **Fixed here:**
  - The quadratic `activitySections` (`77a3307`).
  - The per-row `Intl.DateTimeFormat` construction (`eee4d45`).
  - The index-keyed `Card` rows that remounted every row when one was added at the top (`2c74a7c`).
  - The hostile reducer quadratics (`6a3f55f`; see M5).
- **Recommended:**
  1. Native XChaCha20-Poly1305: a small JSI module over libsodium or CryptoKit-adjacent code, or a vetted RN crypto
     package. This is the one change that moves open from seconds to tens of milliseconds. Keep `@noble` as the
     reference and test vector source.
  2. Until then, yield to the event loop every few hundred envelopes in the derive and in reseals, and show the
     drawn loading state instead of a blank screen.
  3. Share one decode cache between the engine and the state store.
  4. Take `name_cache` and `currency_cache` from the derived state, which already has them, rather than a third pass.
  5. Publish Groups rows as each group finishes, using `name_cache` placeholders, newest first.
  6. Virtualise Expenses and Activity with `FlatList`/`SectionList` (the in-repo pattern is
     `CurrencyPickerSheet.tsx:81`) and memoised rows, matched to the canvas.
  7. Compute usage in SQL: `SUM(length(envelope))` or a stored size per row.

**H4. One client, or a busy launch day, can take the public server's writes, or all of it, offline for a day.
Ops, open.**

- **Where:**
  - The deployed Worker runs on the Workers Free plan.
  - `EVEN_DAILY_WRITE_BUDGET` is 500 append requests a day for the whole server (even-server `a5a8565`; documented in
    `worker/README.md`, "The daily write budget").
  - The per-IP limit is 120 requests a minute. That is 172,800 a day, above the account's 100,000 Workers requests a
    day.
  - The landing site's contact Worker shares the account (`web/wrangler.jsonc:38-41`).
- **Scenarios:**
  - **Large group re-push:** an epoch reset makes every device re-push its whole log at 25 envelopes per append. That
    reset can come from expiry, a deleted server copy, or a move to the public server. A 3,400-event group is 136
    appends per device; three devices take 408 of the server's 500 for the day. After that every user's writes get
    `503 over_budget` until UTC midnight (reads continue).
  - **Ordinary use:** 500 saves a day is the whole budget, and each save is about one append.
  - **One client:** a single client at its per-IP limit can exhaust the account's request quota. Cloudflare then
    answers error 1027 for the sync server and the website until the day resets.
- **Fix:** before launch, decide the plan rather than ship the Free one.
  - The Workers Paid plan raises every quota by orders of magnitude.
  - A WAF rate rule on `sync.even.appalaya.com` and `even.appalaya.com/api/*` stops one address from spending the
    account's quota.
  - A budget sized to expected use, with an alert (even-server `d641227` documents alerts the owner sets up by hand).
  - Nothing to change on the client: it already honours `Retry-After` and, on `over_budget`, pauses pushes until UTC
    midnight while pulls continue. The constraint is the budget, not the client.

### Medium

**M1. A forged `group.rotated` in one group hides another group on the victim's phone and copies their writes
across. Open.**

- **Where:** `src/state/groups.ts:1314-1386` (`rescueFrom`). It acts on any `group.rotated { from }` that names a
  group this phone holds. It never checks that the old group was closed into this one (`group.closed { to }`).
- **Scenario (verified with a harness test):**
  - Mallory is in "Family" (so she knows its `localId`) and in "Climbing club". She writes
    `group.rotated { from: <Family localId> }` into the club.
  - Every phone that holds both groups does three things: syncs Family once, re-encrypts its own Family events into
    the club, and hides Family.
  - The club's members, who never had Family's invite, now read the victim's Family expenses. The club's balances
    count them under "Unknown" members. Family disappears from the victim's phone with no way back: re-joining reads
    as closed.
- **Fix:**
  - Rescue only when the old group's log holds a `group.closed` whose `to` is this group. The rotator always writes
    one (step 6). If it has not arrived yet, recognition runs again on a later sync.
  - Optionally ask "Move your Family entries into Climbing club?" before copying.
  - `design.md` "Recognising a rotation" should state the check.
- **Trade-off:** a straggler whose rotator never got `group.closed` acknowledged keeps the old group visible and
  un-rescued.

**M2. A hostile or broken server can fill the phone's storage, or keep a sync cycle running forever. Open.**

- **Where:**
  - **The pull loop has no bound.** It ends only when `more` is false (`engine.ts:594-675`). The check at `:644`
    catches a page that does not advance, not one that advances forever.
  - **`unsupported_envelope` rows are kept without a cap.** They are classified at `engine.ts:281-286`, and only
    `undecryptable` rows are pruned (`sqliteStore.ts:683-695`).
  - **Pruning happens only at the end of the cycle** (`engine.ts:755-756`).
  - **Response bodies have no size limit** (`src/services/sync/httpTransport.ts:295`).
  - **The client uses server-published `max_batch` and `max_page` unclamped** (`engine.ts:460`, `:605`).
- **Scenario:** an invite can name any server. Such a server can do any of these:
  - answer `more: true` forever with `v: 2` envelopes, which are kept "for a future client";
  - return a 500 MB page;
  - publish `max_batch: 1000000`, so the phone sends its whole outbox in one request body (about 110 MB for 10,000
    maximum-size events).
- **Fix:**
  - A per-cycle page budget derived from a client ceiling (for example 2 × 10,000 entries).
  - Cap `unsupported_envelope` rows as `undecryptable` rows are, and prune every page.
  - Refuse a response whose `Content-Length` is over about 16 MB.
  - Clamp `max_batch` to 100 and `max_page` to 1,000 on the client. Both are allowed by the protocol, since a client
    may send and request less.

**M3. Privacy page and threat model claims the build does not meet. Open; these are document fixes or design
decisions.** Verified here unless marked.

- **"The app offers to copy the code first"** (`web/privacy.html:58`; `THREAT-MODEL.md:117`, "The app's Share sheet
  offers the code first"). The build does not:
  - the share menu offers "Share link" and "Show QR code" (`src/features/group/ShareMenu.tsx:120-122`);
  - Share link is the primary button on both invite cards (`src/features/group/InviteCard.tsx:67`,
    `src/features/groupSettings/InviteCard.tsx:73`);
  - the QR code encodes the link.

  So the stated mitigation for browser history is not there. Either reword both documents, or put Copy code first on
  the canvas.
- **The on-disk list misses the user's own name.** The privacy page says "The only things it writes to storage
  unlocked are…" (`privacy.html:61`), and `THREAT-MODEL.md:85` matches. The `prefs` table also holds `me.name` and
  `me.emoji` in plaintext (`src/state/prefs.ts:145`, `:150`, `:222-225`). That is the user's own member name, asset
  class 2, and it is in Android backups too. Metadata such as `server_url` and `my_member_id` are not content, but
  "only" is too strong. The OS also keeps the app-switcher snapshot and the notification store, both outside the
  app's control. Add the name to both lists, and the snapshot next to the notification note.
- **The contact page holds a pasted invite next to Cloudflare's Turnstile script** (from the web read-through):
  - the page loads Turnstile's `api.js` (`web/contact.html:21`);
  - the CSP allows its frame (`web/_headers:45`);
  - the invite stays in the `#link` field (`web/contact.js:174-189`).

  The page says the link "never leaves this browser" (`contact.html:55`, `privacy.html:97`, `abuse.html:33`). That is
  true of the page's own code, not of a third-party script it runs. Clear the field the moment the id is derived, and
  render Turnstile only after that. Also name Turnstile as a trusted component in THREAT-MODEL.
- **In-app browsers read the `/i` fragment** (from the web read-through). Some chat and social apps open links in a
  WebView that injects its own scripts, which ignore the page's CSP. Add this to "Not defended" next to browser
  history.

**M4. Python reference: settings for self-hosters.** From the Python read-through; its 168 tests passed there.

- **Unlimited total storage by default** (`python/even_server/config.py:31`: budget 0). One IPv4 address can write
  about 12 GB a day within the per-IP limits.
- **Caddy's default error log** writes the request URI, and with it the group id, plus the client IP whenever the
  backend 5xxs (`python/Caddyfile.example`). That breaks PROTOCOL §9.
- **Only the first `X-Forwarded-For` header line is read** (`python/even_server/ratelimit.py:96-98`). Behind a proxy
  that appends a separate line, a client chooses its own rate-limit key.
- **Expiry is one transaction** (`db.py:225-235`), as is `block --purge`, and stalls every request.
- **A new SQLite connection per operation** (`db.py:69-78`) checkpoints the WAL on every request.

Fixes are in the read-through: a default budget or a total-storage cap, a `handle_errors` block in the Caddyfile,
reading every header line, chunked deletes plus an index on `groups(last_write_at)`, and one long-lived connection.

**M5. The reducer was quadratic for three hostile shapes. Fixed in `6a3f55f`.**

- **Where:** `reduce.ts:327-328` (`group.rotated`), `:352-354` (`member.claimed`, copy and re-sort of `devices`), and
  `:371-378` (`member.done`).
- **Scenario:** 10,000 claims of one member from distinct device ids took 1.3 s (V8 with the JIT) on every
  re-derive, and each sync re-derives. 20,000 took 5.5 s. Hermes is far slower.
- **Fix (done):** a set per list inside the fold, with the arrays filled once in `finish` in the same order. 20,000 of
  each now takes about 20 ms. The permutation-invariance property test still holds.

**M6. The Worker's daily expiry is one unbounded batch. Open, and not urgent:** nothing expires until 12 months after
launch.

- **Where:** `even-server/worker/src/db.ts:218-233`. One `batch()` deletes every expired group's events. There is no
  index on `groups.last_write_at` (`worker/schema.sql:22-29`).
- **Scenario:** a year after a spam wave or a busy month, the expiry deletes millions of rows in one D1 transaction.
  The Free plan allows 100,000 rows written a day. The batch fails; because it is all-or-nothing, it fails again every
  day, and nothing ever expires.
- **Fix:** delete a bounded number of groups per run, for example 200 groups through
  `WHERE id IN (SELECT id … LIMIT ?)`, and repeat until done or a budget is reached. Index `last_write_at`.

### Low

**L1. The Worker reads D1 before the per-IP limiter.**

- **Where:** `worker/src/routes.ts:108-119` and `:148-153`.
- **Effect:** a refused request still costs a D1 batch of about 13 rows read. Tokens for fresh random groups are free,
  so passing auth is no barrier.
- **Why it was not committed:** the order is the documented prelude (even-server `design.md` "Request handling",
  steps 4-5), and the Python reference needs the limits row before it can limit. The Worker's limiter thresholds live
  in its bindings, so it could limit first. The Worker request quota (H4) binds well before D1 reads do, so this is
  cost, not availability.
- **Fix, if wanted:**
  - In `prelude`, call `allow(env.RATE_REQUESTS, …)` right after `authenticate`, before `store.groupState`. In `info`,
    call it before `store.loadLimits`. Update the design.md step order to match.
  - The test: pass a refusing fake limiter and a D1 stub that throws on `prepare` and `batch`, then expect `429`, not
    `500`, on `/v1/info`, read, append and delete. That test failed on the current order and passed with the change
    when tried during this review.

**L2. Client `Retry-After` has no ceiling.**

- **Where:** `httpTransport.ts:83-89`, `engine.ts:804-805`.
- **Effect:** a server's `Retry-After: 99999999` puts a hard backoff on the group until the app restarts. Pushes to
  that server stop the same way under `over_budget`.
- **Fix:** clamp to a day.

**L3. Pending-delete tokens never expire.**

- **Where:** `engine.ts:311-317` (network, 5xx, 429 and 503 keep the debt).
- **Effect:** after Leave with "Also delete the copy", a server that has gone away for good leaves its bearer token in
  `pending_deletes` forever. That token is on-disk plaintext, in backups.
- **Fix:** drop a debt after N days or N attempts.

**L4. Bidirectional-control characters in names.**

- **Where:** group names, member names, titles and the invite's `g`. The validator allows U+202A–202E and
  U+2066–2069 (`schema.ts:28-41`).
- **Effect:** a crafted name can reorder text in the Join preview, notifications and Activity. This is spoofing, not
  injection.
- **Fix:** reject these characters in the validator, as an additive tightening for new writes only. Or render names
  isolated.

**L5. The Android App Link filter is broader than the iOS association.**

- **Where:** `app.json:46` uses `pathPrefix: "/i"`, which also matches `/index.html` and any future `/i…` path. The
  iOS file covers `/i` and `/i/*` only.
- **Fix:** `path: "/i"` plus `pathPrefix: "/i/"`.

**L6. Web headers** (from the web read-through):

- no `Cross-Origin-Opener-Policy` (`web/_headers:18-24`), and `/contact` re-applies its fragment on `hashchange`;
- HSTS is set without preload;
- the deploy runs an unpinned `npx --yes wrangler@4` with secrets in its environment (`.github/workflows/web.yml:36`,
  `:116`), and actions are pinned by tag, not commit;
- "every report means a permanent block" invites griefing: `privacy.html:81` and `abuse.html:40` say so, while
  `terms.html:48` says "credible report".

**L7. UI catch blocks log an error's message.**

- **Where:** for example `src/features/join/JoinFlow.tsx:209`, `src/state/groupState.ts:428`.
- **Effect:** a `StoreError` message can quote a local id. That is a hash of the secret, not a server group id, but
  `design.md` asks for fixed words. Severity is low.

**L8. The dev seed and kit ship in the release bundle.**

- **Where:** `src/app/dev/*`, `src/dev/seed.ts` (2,328 lines).
- **Effect:** the routes redirect home when `__DEV__` is false, which was verified: `seed.tsx`, `cleanup.tsx` and
  `kit.tsx`. No attack was found. The code still adds to bundle size and to what a reader must check.
- **Fix:** exclude it from release builds with a Metro `resolver.blockList`, or move it behind a dev-only entry.

  - The audit's suggested fixes are downgrades to Expo 44 and expo-router 5. Do not apply them.
- **even-server/worker:** 5 high, all in dev tooling (`wrangler`, `miniflare`, `undici`, `sharp`,
  `@cloudflare/vitest-pool-workers`). The Worker has no runtime dependencies. Deploys install the locked wrangler
  with `npm ci`.
- **even-server/conformance:** 0.

**Pre-release platform.** The app ships on `react-native@0.88.0-rc.1` and `expo@~58.0.0-preview.7`. This is not a
vulnerability, but move to stable when 58 lands, as `design.md` "Stack" plans.

**Checked and holding**, one line each:

- **Keys and the server boundary:**
  - Keys follow PROTOCOL §2 exactly, with a fixed salt and info strings.
  - The token is per origin, and the group id is SHA-256 of it.
  - `canonicalOrigin` is one parser, used for invites, `group.moved` and key derivation.
  - The AAD binds version, group id, `v` and id.
  - Nonces are fresh from the CSPRNG, guarded against an all-zero source.
  - Padding is ISO 7816-4 to 256-byte classes, and oversize bodies are refused before sealing.
  - Envelope ids are random.
  - The bearer token is sent only to its origin, with `redirect: 'error'`.
- **Validation:**
  - Every decrypted body passes `parseEvent`, which never throws. NaN, Infinity, `-0`, non-safe integers,
    over-length strings, `__proto__` keys (the ids are a 22-character regex, and the reducer's maps are `Map`s),
    unknown `type`/`sv` and strict `changes` are all handled.
  - Deep nesting stays inside `JSON.parse`'s try in `open`, and zod never walks stripped keys.
  - Duplicate ids are replayed once.
  - A second epoch change in one cycle stops the cycle.
- **Invites and links:**
  - The checksum is verified, and the server canonicalised.
  - A payload is taken only from `https://even.appalaya.com/i#…`. `even://` never carries one.
  - `+native-intent` re-encodes the payload into `/join?code=` without parameter injection.
  - Dev routes redirect in release.
  - QR scanning refuses `even://`.
- **Secrets:**
  - Secure store with `AFTER_FIRST_UNLOCK`, serialised index writes, and a check that the secret derives the local id
    before storing it.
  - Recovery rebuilds rows from the index's server URL.
  - Leave deletes rows, records the delete debt with its token, then deletes the secret.
  - A server move reseals byte-exact, drops unreadable rows and clears any debt for the new origin.
- **Server:**
  - Auth comes before any limiter or D1 access.
  - Comparing the token's hash with the group id by `===` is fine: the group id is public (PROTOCOL §2). Python uses
    `compare_digest`.
  - A missing group reads as empty `200`, so existence does not leak.
  - The body cap is enforced on the stream.
  - Caps and the budget live in triggers, so batches are atomic and exact.
  - `no-store` and CORS `*` are on every response.
  - Log lines carry the route pattern only. Invocation logs, traces and Logpush are off.
- **Landing page:**
  - `/i`'s CSP is exactly as `design.md` states, with current hashes.
  - It inserts the group name with `textContent` only.
  - It makes no network calls, and "Open in Even" carries no payload.
  - The contact Worker validates every field, keeps CR/LF out of mail headers, and fails closed on Turnstile.
- **In-app browser targets:** fixed `https://even.appalaya.com/…` pages and GitHub. A server's `terms` is opened only
  when it is an https URL.
- **CSV export:** guards against formula injection.

## The 10,000-event group

The synthetic log has:

- 50 members, each with `member.added` and `member.claimed`;
- one `group.created`;
- about 6,700 live expenses, split among 2 to 11 members;
- about 2,000 title edits, about 500 payments, about 200 deletes, and done/undone marks;
- 9,730 activity items.

Envelopes were sealed with core, stored through the real `SqliteStore` on `node:sqlite`, and derived through the
app's `GroupStateStore`. Each stage ran once, warm, on an Apple-silicon Mac.

| `nets` / `simplify` | 5 ms / 0.1 ms | 6 ms / 0.1 ms |
| `activitySections` before `77a3307` → after | 25 → 4 ms | 61 → 6 ms |
| `sortedExpenses` | 1.3 ms | 2.1 ms |

Hostile shapes in the reducer, V8 with the JIT:

Other measurements:

- **`activitySections`, 10,000 items among 10,000 members:** 2,900 ms before, 8 ms after. Hostile placeholders make
  this size reachable: 1,000 expenses each splitting among 50 never-added ids create 50,000 members, in 1.8 MB.
- **Clock times for a 30,000-row Activity:** 400 ms before `eee4d45`, 8 ms after. A new `Intl.DateTimeFormat` costs
  about 50 times a `format` call.

Nothing else is quadratic in core or the store:

- `nextTs` is one pass per write.
- `nets` and `simplify` are linear and n log n.
- The outbox query uses its partial index and sorts only pending rows.
- `latestTs` uses `events_ts`.

Every SQLite query is keyed by `local_id` through the primary key or an index. `listReadable` and `listEnvelopes`
sort by the `ts IS NULL, ts, id` expression, which no index serves. For 10,000 rows that sort costs milliseconds, not
seconds.

Server side, from the code and the Python read-through:

- An append is constant-time per envelope: `MAX(seq)` and the duplicate check both use the primary key or unique
  index.
- A page is an indexed range scan with `LIMIT + 1`. A full 10,000-event pull is 20 pages.
- A full re-push is 400 appends per device, at least 6 min 40 s at 60 writes a minute. Devices behind one NAT share
  that limit.

## Not verified without a device

- Hermes timings. `--jitless` V8 is a proxy, and the date and number formatters behind Hermes's `Intl` differ from
  ICU.
- That an uncaught render error is fatal in the release build. This was inferred from the absence of any
  `ErrorBoundary` export.
- That React Native's `fetch` honours `redirect: 'error'`, and whether a redirect would carry the `Authorization`
  header.
- That Hermes's `JSON.parse` turns an 8 KB deeply nested body into a catchable error rather than a native stack
  overflow. V8 parses it.
- Universal link and App Link routing through `+native-intent` at cold and warm start.
- How long background refresh runs with a large backlog against its 25 s deadline.
- Frame times and memory with 6,000 mounted rows.
- Keychain persistence across reinstall, and Android keystore behaviour after a restore.
- What the lock screen shows from notifications.
- Cloudflare account settings: plan, WAF rules, Always Use HTTPS, Rocket Loader, Zaraz and Web Analytics. Also what
  Workers Logs attaches to a `console.log` line with invocation logs off, and whether `assetlinks.json` carries the
  Play App Signing fingerprint.
